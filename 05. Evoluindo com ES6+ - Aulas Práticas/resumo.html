DevOps

Um Resumo Detalhado do Capítulo 10

1. Introdução ao DevOps

Historicamente, as áreas de TI eram divididas em **Desenvolvimento (Dev)** e **Operações (Ops)**. Isso criava um "silo" onde a equipa de operações só tomava conhecimento de um sistema na véspera da implantação, causando atrasos, problemas de infraestrutura e stresse.

"Imagine a world where product owners, development, QA, IT Operations, and Infosec work together, not only to help each other, but also to ensure that the overall organization succeeds."

- Gene Kim, Jez Humble, et al.

O que é DevOps?

DevOps é um movimento que visa unificar as culturas de **Dev** e **Ops** para permitir a implantação mais rápida, ágil e menos traumática de um sistema. A ideia é que estes profissionais atuem em conjunto desde os primeiros sprints, antecipando problemas e automatizando a entrega.

2. Princípios da Entrega de Software (Jez Humble & David Farley)

  • Crie um processo repetível e confiável: A entrega de software não pode ser um evento manual e traumático. Deve ser tão simples como "apertar um botão".
  • Automatize tudo que for possível: Build, testes, configuração de servidores, carga de banco de dados, etc.
  • Mantenha tudo em um sistema de controle de versões: Não apenas o código, mas scripts de administração, documentação, arquivos de dados, etc.
  • Se um passo causa dor, execute-o com mais frequência: O exemplo clássico é a integração. Se integrar causa dor, integre mais frequentemente (Integração Contínua).
  • "Concluído" significa pronto para entrega: A funcionalidade deve estar 100% pronta para ir para produção.
  • Todos são responsáveis pela entrega: Quebra os silos entre desenvolvimento e operações.

3. Controle de Versões (VCS)

Fundamental para a colaboração, permite armazenar o código num repositório central e manter um histórico de todas as alterações, permitindo "voltar no tempo".

VCS Centralizado vs. Distribuído (DVCS)

VCS Centralizado (Ex: Subversion - SVN)

Arquitetura cliente/servidor. Existe um único servidor. O "commit" é feito diretamente no servidor central.

VCS Distribuído (Ex: Git, Mercurial)

Arquitetura peer-to-peer. Cada programador tem um repositório local completo. O "commit" é feito localmente e depois sincronizado ("push"/"pull").

Vantagens do DVCS:
  • Trabalho offline.
  • Commits mais rápidos e frequentes.
  • Maior flexibilidade na sincronização.

Git vs. GitHub

  • Git: É o sistema de controle de versões distribuído (DVCS) criado por Linus Torvalds. É a ferramenta de linha de comando que gere o código.
  • GitHub: É um *serviço de hospedagem* para repositórios Git (como o GMail é um serviço para email). Oferece uma interface web, gestão de repositórios, pull requests, etc. (Alternativas: GitLab, BitBucket).

Multirepos vs. Monorepos

Multirepos

A abordagem tradicional. Um repositório para cada projeto (ex: `empresa/sistema1`, `empresa/sistema2`).

Monorepos

Um único repositório para *todos* os projetos da organização (ex: `empresa/codigo`, com subdiretórios `sistema1`, `sistema2`). Usado por Google, Facebook, Microsoft.

Vantagens do Monorepo:
  • Única "fonte da verdade".
  • Incentiva o reúso de código.
  • Mudanças atómicas (um único commit afeta vários sistemas).
  • Facilita refatorações em larga escala.

4. Integração Contínua (CI)

A Motivação: O "Inferno da Integração"

Tradicionalmente, programadores trabalhavam isolados em *branches de funcionalidades* (feature branches) por semanas ou meses. Quando tentavam juntar (fazer `merge`) o seu código de volta ao `master`, ocorriam inúmeros conflitos, pois o `master` já tinha mudado muito. Resolver isso era um processo manual, doloroso e imprevisível.

O que é Integração Contínua (CI)?

É uma prática do XP baseada no princípio: "se causa dor, faça com mais frequência". Como grandes integrações causam dor, CI recomenda integrar o código de forma frequente e contínua.

Pelo menos uma integração por dia, por programador.

Com isso, as integrações são pequenas, geram menos conflitos e os problemas são detetados imediatamente.

Boas Práticas para uso de CI

  • Build Automatizado: O processo de compilar e gerar a versão executável do sistema deve ser 100% automático e rápido (idealmente < 10 minutos).
  • Testes Automatizados: Garantir que o novo código não quebrou nada. Essencial para a segurança da prática.
  • Servidores de CI: Ferramentas (como Jenkins, Travis CI, GitHub Actions) que automaticamente detetam um novo commit, clonam o repositório, rodam o build e os testes, e notificam a equipa em caso de falha.
  • Desenvolvimento Baseado no Trunk (TBD): Evitar branches de longa duração. Todo o desenvolvimento acontece no `master`/`trunk`. Usado por Google e Facebook.
  • Programação em Pares: Considerada uma forma de "revisão de código contínua".

Quando não usar CI? (ou adaptar)

O limite de "1 commit por dia" pode não ser realista para todas as equipas. A prática deve ser adaptada. No entanto, CI não é compatível com projetos de código livre (onde programadores são voluntários e não têm obrigação diária), que dependem mais de *Pull Requests* e *Forks*.
